# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

# Project rules

TypeScript monorepo, pnpm workspaces. Project facts (name, domain, languages,
data sensitivity) are in PROJECT.md. Design values are in DESIGN.md.

## Structure
```
apps/
  backend/                  @repo/backend: Fastify + zod, Prisma, PostgreSQL
    prisma/
      schema.prisma         single source of truth for the database
      migrations/           generated by Prisma, committed
    prisma.config.ts        Prisma CLI config, loads .env
    src/
      main.ts               entry point, starts the server
      server.ts             app setup, plugin registration, zod compilers
      config.ts             environment variables, validated with zod
      errors.ts             typed errors thrown by services
      generated/            Prisma client, generated and not committed
      routes/               one file per resource, each exports a Fastify plugin
      services/             business logic, no Fastify imports
      db/                   the single PrismaClient instance
      plugins/              cross-cutting plugins (auth, db, error handler)
      auth/                 passwords (scrypt) and sessions (hashed tokens)
      cli/                  backend commands: login:create, login:set-password, member:set-role
  frontend/                 @repo/frontend: React + Vite, TanStack Query
    src/
      main.tsx              entry point, providers
      api/                  typed fetch client, one file per resource (hooks)
      features/             one folder per feature: components, hooks, local types
      components/           small reusable UI components, no business logic
      lib/                  utilities, formatting helpers
      routes/               page-level components or router config
  mobile/                   @repo/mobile: Expo (React Native), Expo Router, TanStack Query
    app.config.ts           Expo config, config plugins
    app/                    file-based routes (Expo Router)
      _layout.tsx           root layout, providers
    src/
      api/                  typed fetch client, one file per resource (hooks)
      features/             one folder per feature: components, hooks, local types
      components/           small reusable UI components, no business logic
      theme/                design tokens from DESIGN.md
      lib/                  utilities, formatting helpers
packages/
  shared/                   @repo/shared: zod schemas, types, and client code
    src/
      types/                imported as "@repo/shared", by all apps
        <resource>.ts       schemas and types for one resource
        common.ts           pagination, id, errorResponse
      auth/                 imported as "@repo/shared/auth", by all apps
        roles.ts            LOGIN_ROLES: which member roles may log in
        abilities.ts        defineAbilityFor: CASL rules, what each role may do
      client/               imported as "@repo/shared/client", by frontend and mobile
        apiClient.ts        createApiClient: fetch, parse with zod, ApiError
```

## Boundaries
- Dependency direction: backend -> shared, frontend -> shared,
  mobile -> shared. The three apps never import from each other. Shared
  imports only zod and @casl/ability, and must run in the browser, Node, and
  React Native.
- The backend imports only `@repo/shared`, never `@repo/shared/client`.
- Apps may import `@repo/enrollment`. It imports nothing: no other workspace
  package, no Prisma, Fastify, React, or DOM APIs. Its tests use fake data
  only.
- Code that frontend and mobile both need, and that does not touch the DOM,
  React Native, or React, goes in shared `client/` instead of being copied.
- All API request/response schemas live in shared as zod schemas. Types are
  inferred with z.infer. Never duplicate a type or hand-write an interface a
  schema covers.
- One zod version, the same in all packages.
- Only edit the package the task concerns, unless I say otherwise.
- When adding a dependency, install the latest stable version, then pin it
  (exact, no ^ or ~). Mobile: use the latest Expo SDK, and for packages the
  SDK manages, the version `npx expo install` picks.

## Commands
Tooling: Node 26 (`.nvmrc`), pnpm 12, TypeScript 7, oxlint. Versions shared
by several packages are set once in the `catalog` in `pnpm-workspace.yaml`.

Always run per package, never for the whole repo.
- docker compose up -d starts PostgreSQL on port 5433 with a dev and a test
  database. Backend dev and backend tests both need it running.
- pnpm --filter @repo/<pkg> dev | build | test | lint | typecheck
- pnpm --filter @repo/backend prisma <command>
- The apps consume shared through its build output, not its source. A stale
  build shows up as type errors or missing exports in the apps, so after
  every change to shared run, in this order:
  1. pnpm --filter @repo/shared build
  2. pnpm --filter @repo/backend typecheck
  3. pnpm --filter @repo/frontend typecheck
  4. pnpm --filter @repo/mobile typecheck
  If an app reports a shared type or export that looks wrong, rebuild shared
  before debugging the app.
- The same holds for enrollment: after a change, run
  `pnpm --filter @repo/enrollment build`, then typecheck backend and frontend.
- Tests use Vitest. Mobile is the exception: Jest with the `jest-expo` preset.
- Single test file or test, Vitest packages (shared, enrollment, backend, frontend):
  pnpm --filter @repo/<pkg> test <path/to/file.test.ts> -t "<test name>"
- Single test file or test, mobile (Jest):
  pnpm --filter @repo/mobile test <path/to/file.test.tsx> -t "<test name>"
- Mobile has no `build` script. `dev` runs `expo start`; app builds go
  through EAS.

## Conventions
- API errors: one response shape for all errors, defined once in shared
  (`errorResponse` in common.ts), with a stable machine-readable `code` and a
  human-readable `message`. Never expose stack traces or internal details.
- Dates and times: stored and transferred in UTC as ISO 8601 strings.
  Converted to local time only for display, through a shared helper.
- IDs: opaque strings in the API contract.
- Logging: structured logs. Never log personal data, secrets, or tokens.
- Config: secrets and environment-specific values come from environment
  variables, validated with zod at startup. Commit `.env.example`, never `.env`.

## Shared
- Define a zod schema first, then export its type with z.infer.
- Name schemas by role: createUserBody, updateUserBody, userResponse,
  listUsersQuery. Types use PascalCase: CreateUserBody, UserResponse.
- `types/`: no business logic and no side effects. Only schemas, types, and
  constants.
- `auth/`: roles that may log in and the CASL abilities. Every permission
  rule lives in `defineAbilityFor`; routes and screens only ask
  `ability.can(action, subject)`, never check a role directly.
- `client/`: pure functions for the client apps (API client, query keys and
  query options, request functions, form logic, formatting). No React or
  TanStack Query imports: export plain query option objects and let each app
  wrap them in hooks, so an app never bundles two copies of React. No side
  effects at import time. Form logic returns error codes; each app maps them
  to its own messages.
- Response schemas describe what clients receive, not database rows. Never
  include password hashes or internal flags.
- Dates use zod's ISO datetime validator, never a plain string.
- After changing an existing schema, tell me which fields changed.

## Backend
Routes
- Every route declares schemas for body, params, querystring, and every
  response status code it can return, using schemas from @repo/shared.
- Use `app.withTypeProvider<ZodTypeProvider>()`.
- Handlers stay thin: parse, call a service, return. No business logic or
  direct database access in handlers.
- Every route declares the ability it needs with
  `onRequest: app.requireAbility(action, subject)`, or `app.requireSession`
  for routes about the logged-in member. Only `POST /auth/login` is open.
  `onRequest`, not `preHandler`: it runs before body validation, so logged-out
  callers get 401, not validation details. Declare 401 and 403 in its
  response schemas.
- Register routes as plugins in server.ts with a URL prefix per resource.

Services and database
- Services are plain functions with typed input and output that know nothing
  about Fastify.
- One PrismaClient instance, created in src/db and shared via a plugin.
- Never return Prisma models from a route. Map them to the shared response
  schema, using `select` or explicit mapping.
- Use `prisma.$transaction` when several writes must succeed or fail together.
- Avoid `$queryRaw` unless Prisma cannot express the query. Never build SQL
  by string concatenation.

Prisma
- Change the schema only in prisma/schema.prisma, then run
  `prisma migrate dev --name <short-name>` and confirm the client is regenerated.
- Never edit generated client files or an existing migration.
- Model names singular PascalCase, fields camelCase. Every `DateTime` field
  uses `@db.Timestamptz`.
- Table names lowercase (`@@map`), ids autoincrement integers.
- Fixed value sets are Postgres enums, not text.
- In production only `migrate deploy` is allowed.

Errors
- Services throw typed errors. A single error handler plugin maps them, and
  known Prisma errors (unique constraint, record not found), to the shared
  `errorResponse` shape.

Testing
- Test services directly against a separate test database, never the
  development or production one.
- Test routes with `app.inject()`, no real network.
- Every new route needs at least one success test and one validation-failure test.

## Frontend
Components
- Function components with hooks. One component per file, named exports,
  PascalCase file names.
- Data fetching lives in hooks in api/ or features/, not inline in JSX.
- Handle loading, error, and empty states for every data-driven view.
- Accessibility: semantic elements, labels on inputs, buttons for actions and
  links for navigation, keyboard-usable controls.

Data
- All server communication goes through the typed client in src/api. No raw
  `fetch` anywhere else.
- TanStack Query for server state: `useQuery` for reads, `useMutation` for
  writes, stable query keys defined in one place per resource. Invalidate the
  relevant queries after a successful mutation.
- Parse API responses with the shared zod response schema.
- Do not copy server data into local state with useState or useEffect.
- Local component state for UI state only.

Forms
- Validate with the same request schemas from @repo/shared.
- Show field-level errors next to the input. Disable submit while the request
  is in flight.

Text
- Languages are listed in PROJECT.md. Build translation-ready: no hardcoded
  user-facing strings in components. Keep them in one central messages file,
  referenced by key.
- User-facing error messages come from the same messages, keyed by the API
  error `code`.
- Format dates, times, numbers, and money through a helper in lib/. No
  hardcoded formats. No text inside images.

Styling
- Follow DESIGN.md. Do not invent colors, fonts, or spacing values.
- Design tokens are defined once as CSS custom properties in a single tokens
  file. Components use the variables, never raw hex values.
- Follow the styling approach already in the project.

Testing
- Vitest and Testing Library, focused on user-visible behavior. Mock the API
  client, not React internals.
- Every new feature needs at least one test for its main flow.

## Mobile
Setup
- Expo with Expo Router. The ios/ and android/ folders are generated by
  prebuild and never committed or edited by hand. Native configuration goes
  through app.config.ts and config plugins.
- Prefer Expo SDK packages over third-party native modules. Ask me before
  adding a native module or a config plugin.
- Add Expo packages with `npx expo install` so the version matches the SDK,
  then pin the version it wrote to an exact one.
- The app must work on both iOS and Android. Use `Platform.select` or
  `.ios.tsx` / `.android.tsx` files only where the platforms really differ.

Components
- Function components with hooks. One component per file, named exports,
  PascalCase file names.
- Data fetching lives in hooks in api/ or features/, not inline in JSX.
- Handle loading, error, empty, and no-connection states for every
  data-driven screen.
- Respect safe areas and the on-screen keyboard on every screen.
- Use `FlatList` or `SectionList` for lists of unknown length, never `map`
  inside a `ScrollView`.
- Accessibility: `accessibilityLabel` and `accessibilityRole` on interactive
  elements, touch targets at least 44x44 points.

Navigation
- Routes are files in app/. Route files stay thin: read params, render a
  screen component from features/. No business logic or data fetching in them.
- Enable Expo Router typed routes. Never build route paths by string
  concatenation.

Data
- All server communication goes through the typed client in src/api. No raw
  `fetch` anywhere else.
- TanStack Query for server state, with the same rules as the frontend:
  stable query keys per resource, invalidate after a successful mutation, no
  copying server data into local state.
- Parse API responses with the shared zod response schema.
- The API base URL and other environment values come from `EXPO_PUBLIC_`
  variables, validated with zod at startup. They are bundled into the app
  and readable by anyone, so never put a secret in one.
- Tokens and other sensitive values go in `expo-secure-store`, never in
  AsyncStorage.

Forms
- Validate with the same request schemas from @repo/shared.
- Show field-level errors next to the input. Disable submit while the request
  is in flight. Set the right keyboard type and autofill hints per input.

Text
- Same rules as the frontend: no hardcoded user-facing strings, one central
  messages file referenced by key, error messages keyed by the API error
  `code`, and all date, time, number, and money formatting through a helper
  in lib/.

Styling
- Follow DESIGN.md. Do not invent colors, fonts, or spacing values.
- Design tokens are defined once in theme/. Styles use `StyleSheet.create`
  and the tokens, never raw hex values or loose numbers.
- Layouts must hold on small and large phones and with larger system font sizes.

Testing
- Jest (`jest-expo` preset) and React Native Testing Library, focused on
  user-visible behavior.
  Mock the API client, not React Native internals.
- Every new feature needs at least one test for its main flow.

## Code style
- Strict TypeScript, no `any`, no non-null assertions without a comment.
- Prefer small, pure functions. No dead code, no commented-out code.
- Comment only non-obvious code.
- Do not change unrelated files or reformat code you are not editing.
- Small commits with a short imperative message.

## Ask first
Ask me before any of these. Do not guess.
- New or changed features and requirements.
- API contract changes.
- Database schema changes; renaming, dropping, or retyping columns or tables.
  Describe the data impact first.
- Anything touching authentication or authorization.
- New personal data fields.
- New dependencies, libraries, global state, i18n, or styling approaches.
- Design values not in DESIGN.md.
- New device permissions (camera, location, notifications, contacts).
- EAS builds, store submissions, and over-the-air updates.
- Destructive commands (`migrate reset`, `db push`, deleting files or branches).

## Working method
- For cross-cutting work, go in order: shared, backend, frontend, mobile.
- Before finishing, run typecheck, lint, and tests for every package you touched.
- Finish with a short summary: what changed, which shared schema fields
  changed, and for UI work what I must check visually (breakpoints, contrast,
  focus states; on mobile both platforms, small and large screens).
- If blocked or unsure, stop and ask.
